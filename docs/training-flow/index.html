The two obvious duplicate-work candidates are rebuilding each player's observation twice per step and sampling an action only to zero it. Neither requires a full C port. A faster worker also does not automatically eliminate pipe traffic or the all-worker barrier.

  
01 / Score movement toward a target
dx = player_x − target_x
dy = player_y − target_y
current_distance = sqrt(dx² + dy²)
progress_reward =
  2 × (previous_distance − current_distance)
For example, a distance change from 5.0 to 4.9 gives +0.2 for this reward term. Target bonuses, edge penalties and fall penalties are computed separately. Illustrative numbers, not a recorded trajectory.

  
02 / Encode the next observation
observed_x = max(-18, min(18, x))
observed_vx = max(-10, min(10, vx))
observed_damage = damage / 700
grounded = 1.0 if is_on_floor() else 0.0
Read the current world, clamp values and build an array. Example: x = 20 produces observed_x = 18. This does not move the character; it prepares information for the model.

Read the timing limits, sources and CPU/GPU misconceptions
    
This is a diagnostic, not a stable baseline. The measured window was 9.426802 seconds for 16,384 transitions (1,738.02 steps/s). One-round bars reconstruct the ordering from averages; they are not the timestamp trace of one actual round. The average includes rounds with automatic resets. Within-round control/timer residual is shown explicitly. Startup, learning updates, rollout-end work and between-rollout setup are excluded from that round axis.

    
The complete run also includes 0.937602 seconds of learning, 0.016110 seconds of rollout-end callbacks/value/advantage work and 0.056898 seconds outside rollouts/updates. Learning updates varied substantially: 0.94 seconds in this probe versus 3.82–4.41 seconds nearby. The cause remains unresolved. Full-episode timing is unavailable: the walkthrough is not a recorded episode. The detailed 1-env result was not retrieved and is not used here.

    
  • Already parallel: 16 persistent CPU processes advance 16 independent worlds. They do not split one world's physics across 16 processes. All 16 results are required before the next action round.
  • GPU occupancy is not the goal: useful training throughput and learning quality are. Unnecessary GPU work can raise usage without helping. No utilization or kernel trace here proves the GPU is completely idle during every CPU interval.
  • RAM ≠ VRAM: the game state stays in host RAM. Numeric observations and training batches cross to VRAM; predictions return. The model weights do not cross back and forth every step.
  • No measured bandwidth bottleneck: payload sizes below are shape calculations, not measured PCIe traffic. Copy stages can include waiting for GPU work. A long copy call does not by itself mean the cable is saturated.
  • Inference ≠ learning: inference chooses actions with current weights. PPO learning changes weights after a rollout of 8,192 transitions, potentially spanning many episodes.

    
Shape-derived float32 payloads: 16 × 2,656 observations = 166 KiB per round; 16 × 10 actions = 640 B; values + log probabilities = approximately 128 B. An 8,192-observation training batch alone is 83 MiB, before other arrays. Physical transactions/extra copies were not measured.

    
Sources: profiling report · raw profile · game engine · training wrappers. Source snapshot: 2026-09-04 EDT; SB3 2.5.0 / Torch 2.4.1+cu121.

Worlds on the Chip

What the GPU-resident simulator proposal actually means at the hardware level: where the speedup comes from, what "parallel" means for a game, and how thousands of games sit on one graphics card.

What is this document? A design for the next experiment, not a result. It proposes rewriting the game simulation so the games themselves run as CUDA code on the GPU, next to the model. Nothing has been built yet beyond a small moving-platform prototype.

Is the speedup from putting more environments on the GPU? Partly, but that is not the main thing. The main win is that each tick stops paying for two things it pays for now: the CPU running Python game logic, and the CPU and GPU handing data back and forth. Once a tick is cheap, you can also run many more worlds. Both matter, in that order.

How does it run on the chip? One kernel launch advances every world by one tick at the same time. Each world is handled by a GPU thread (or a small group of them). Thousands of threads execute the same tick function on different worlds' numbers in lockstep.

1. Where the time goes today

Every training step today is a round trip. The picture below is one tick for a batch of 256 environments. Read it left to right as wall-clock time.

The GPU is busy for one narrow slice. The rest of the tick, it waits for the CPU to finish Python, Pymunk, and process-to-process messaging, then for the observations to cross the bus. Adding more environments on the CPU side stretches the amber blocks. It does not shrink the grey ones.

That is why the current 256-environment run sits near 17,772 steps per second. The number is set mostly by how fast the CPU can produce observations, not by the GPU.

2. What changes with a GPU-resident simulator

Same tick, same batch, but the game-step code is a CUDA kernel and the state never leaves VRAM.

One tick, GPU-resident · 256 or more worlds · same time scale
CPU workGPU workidle

Two things happened. The amber blocks are gone because the game logic is now a GPU kernel. The bus transfers are gone because the observation tensor the model reads is the same buffer the step kernel wrote. Ticks now sit back to back on the GPU.

So where does the speedup come from, precisely?

SourceWhat it removesDepends on more worlds?
No Python per tickInterpreter overhead, object allocation, Pymunk call boundaries, worker-process messagingNo. Applies at 256 worlds.

One kernel steps all worldsThe cost of a tick barely grows as you add worlds, until the chip is fullYes. This is the part that scales.

So the honest answer to "are we just putting more environments on the GPU" is: first we make one tick cheap for the batch size we already use. Then, because a GPU tick for 4,096 worlds costs about the same as for 256, we can raise the world count almost for free. The design doc treats those as separate measurements, which is why it fixes 256 worlds for the first comparison.

3. How it actually runs on the chip

A GPU is not one fast processor. It is many slow ones that all run the same instruction at once. On a typical training card:

  • The chip has on the order of 100 to 130 streaming multiprocessors (SMs). Each is an independent little processor.
  • Each SM runs threads in groups of 32 called warps. All 32 threads in a warp execute the same instruction on the same clock, each on its own data.
  • Each SM can hold many warps at once, typically up to 64, and swaps between them whenever one is waiting on memory.

The simulator's step is written once, as a function that advances one world by one tick. CUDA then runs that function on every world in parallel. The simplest mapping is one thread per world: thread 0 advances world 0, thread 1 advances world 1, and so on.

One tick as a kernel launch · one thread per world
step_kernel<<<blocks, 256 threads>>>(state, actions, obs_out, reward_out);

__global__ void step_kernel(WorldState s, Actions a, Obs o, Reward r) {
    int w = blockIdx.x * blockDim.x + threadIdx.x;   // which world am I?
    if (w >= NUM_WORLDS) return;

    read_controller(s, a, w);      // decode held / newly pressed buttons
    move_platforms(s, w);          // moving-platform path + reversal
    apply_player_physics(s, w);    // gravity, run, jump, dodge state
    resolve_contacts(s, w);        // the hard part: landing, sides, undersides
    update_curriculum(s, r, w);    // target hold, fall, success, timeout
    write_observation(s, o, w);    // 64 values into obs_out[w]
    if (episode_done(s, w)) reset_world(s, w);   // only this world
}

The function body reads like the ordinary game loop. What is parallel is not the inside of the function. It is that the same function runs for every value of w simultaneously. World 17 cannot skip ahead of itself, but it never has to wait for world 18.

Why the state becomes flat arrays

Thread w needs to find its world's data by arithmetic, not by following Python object pointers. So the state becomes buffers indexed by world:

player_position [world][player][xy]     float32
player_velocity [world][player][xy]     float32
movement_state  [world][player]         uint8
platform_position [world][platform][xy] float32
target_position [world][xy]             float32
target_hold_ticks [world]               int16
episode_ticks   [world]                 int16

When 32 neighbouring threads read player_position[w] for 32 neighbouring worlds, the memory system fetches one contiguous strip. That is the layout the hardware is built for, and it is the second reason the doc says layout will be chosen by measurement rather than by copying the Python class structure.

Lockstep and divergence

The lockstep rule has a cost. If world 5's player is mid-jump and world 6's player is dodging, the warp cannot run the jump code and the dodge code at the same instant. It runs the jump branch with the dodge threads masked off, then the dodge branch with the jump threads masked off. Lanes that are masked do nothing useful. Try it:

Red lanes are masked off while another branch runs. Fewer distinct branches per warp means fewer passes. This is why compact state and careful branching matter as much as the language, and why "one thread per world" is a starting point, not a given.

Filling the chip

The other question is whether the game step alone even fills the GPU. It does not, at modest world counts. Slide the world count and watch how much of the chip the step kernel touches.

At 256 worlds the step kernel occupies a sliver of the chip. That is fine: the win at 256 is removing the CPU and the bus, not saturating the GPU. The model forward pass is what fills the SMs, and it is already batched. Raising worlds toward 4,096 or beyond is what starts to make the simulator itself use the hardware, and the doc treats that as a second, separate experiment because it also changes trajectory length per rollout.

4. The model and the simulator share the chip

Within one tick there are two kernels on the same GPU, in sequence:

  1. Model forward. A batched matrix-multiply over all worlds' observations, shape [worlds, 256] in, actions and values out. This is dense, uniform work and already keeps SMs busy.
  2. Step kernel. Branchy per-world logic, light on arithmetic, sensitive to memory layout and divergence.

They do not run at the same time in the initial design; the step needs the actions, and the next forward needs the new observations. So GPU utilisation near 100% is not the goal. The goal is that the sum of the two is much shorter than the current tick, and that no time is spent waiting on the CPU in between.

PPO's update phase is unchanged. The rollout buffer that the step kernel fills is the same device tensor the learner reads, so the eight training passes also skip the bus.

5. What could make it not work

  • Collision fidelity. Pymunk is already native C. Rewriting it in CUDA gives no speedup by itself and risks a player landing in one engine and falling in the other. This is the first gate in the plan.
  • Divergence. If worlds spend most ticks in different branches, the warp runs every branch every tick and the kernel gets slow. Measurement decides the thread mapping.
  • Reset correctness. Each world resets alone, inside the kernel, and the final observation must be saved before the reset overwrites it. A bug here corrupts value targets quietly.
  • Silent fallback. A run that quietly steps on the CPU while claiming to be GPU-native would produce a misleading benchmark. The design requires this to be an explicit error.

6. One-paragraph version

Today the GPU spends most of each tick waiting for the CPU to run Python games and push observations across the bus. The proposal moves the game itself onto the GPU as a kernel that advances every world at once, one thread per world, over flat arrays of numbers. The immediate speedup comes from deleting the CPU work and the bus copies at the batch size we already use. A second, later speedup comes from raising the world count, which costs the GPU almost nothing per extra world until the chip fills. The risk is not speed. It is making thousands of lockstep worlds land on platforms exactly the way the original Pymunk game does.

# CPU Simulation and Batching Options

## Synthesis

The strongest CPU-side lesson from the literature is that "rewrite the game in C" and "put the game on the GPU" are not the only choices. A large part of RL training time is often lost at the boundary between many environment copies, policy inference, rollout storage, and process communication. EnvPool, PufferLib, and Sample Factory all attack that boundary by keeping environment work continuously fed, batching results in fixed-size memory, and reducing serialization/copy overhead. For this repo, where Pymunk physics is already native C but the game orchestration, observations, rewards, histories, wrappers, and vectorized training path still involve Python, the next CPU-side bet should be to test a batched/vectorized runner shape before rewriting the full engine.

My research conclusion for this lane: first explore CPU batching/transport and selective compiled hot paths. A full C environment may become the right endpoint, but this lane's working hypothesis is that we should test the combined runner shape first: contiguous state, preallocated buffers, multiple envs per worker, async or double-buffered stepping, and only then C/Cython for the remaining per-step logic. A direct full-engine C rewrite is expensive and easy to make behaviorally different. A GPU simulator rewrite is a separate architecture track with higher rewrite cost and stricter constraints on environment structure; this note covers only CPU simulation and data flow.

Recommended experiment sequence for this lane: measure the latest code at production-like env counts supported by the available CPU cores, add a tiny shared-memory or preallocated-buffer prototype that preserves current Python game semantics, sweep `num_workers`, `envs_per_worker`, and batch size, then compile only the hot Python loops that remain. The pass/fail test should be end-to-end wall-clock time-to-same-training-budget and replay equivalence, not raw environment FPS alone.

## Possible CPU Action Space

1. **Keep optimizing Python hot paths.** This is the lowest-risk lane: remove duplicate observation/reward/history work, avoid unnecessary object allocation, stop rebuilding static data, and make arrays contiguous. It preserves behavior and improves both local CPU runs and GPU-backed training. The downside is that gains shrink once the obvious duplicate work is gone.

2. **Selective compiled hot paths.** Instead of rewriting everything, compile the tight loops that profiling proves are still hot: observation assembly, player state packing, history updates, collision-derived reward bookkeeping, or action decoding. This can be Cython, pybind11/C++, Rust, or Numba depending on local constraints. The literature supports native code when the environment itself is Python-bound, but the proof must show the remaining bottleneck is actual Python bytecode rather than Pymunk, policy inference, rollout buffers, or process scheduling.

3. **Contiguous state and batched stepping.** EnvPool and PufferLib both organize environment results as fixed-size arrays rather than many small Python objects. For this game, a bounded prototype could keep the existing Python environment but write observations, rewards, dones, truncations, and compact infos into preallocated arrays. This directly tests whether object packing and wrapper aggregation are costing enough to matter.

4. **Shared-memory transport.** Sample Factory and PufferLib both reduce communication by putting bulky tensors/arrays in shared memory and sending small handles or flags. This is not the PCIe cable. It is CPU RAM shared between processes on the same machine. The GPU transfer over PCIe is a separate path for policy inputs/outputs. A good test here is to replace per-step pickled pipe payloads with shared observation/action buffers while keeping episode infos rare and small.

5. **Multiple games per worker.** PufferLib and Sample Factory both use the idea that one process can own several env instances. This can lower the number of tiny processes and can better amortize worker startup, pipes, wrapper overhead, and policy latency, but it does not necessarily beat one env per process for this game. It does use more RAM because each env still has state, but the limiting resource is not just RAM; useful scaling also depends on CPU cores, cache behavior, process scheduling, step-time variance, and how fast each worker can supply batches.

6. **Async or double-buffered collection.** EnvPool's `batch_size < num_envs` and Sample Factory's double buffering both reduce waiting on slow envs or on policy inference. Double-buffered inference can still keep policy weights frozen during rollout collection, preserving on-policy PPO behavior for that rollout. Overlapping learning updates with ongoing sampling from older policy weights is the version that creates policy lag and needs correction or learning-curve checks. A bounded version can still be tested as a runner-level option with deterministic replay checks.

7. **Trainer-side CPU work.** The EnvPool paper separates pure simulation FPS from end-to-end agent training. In this repo, prior profiling already suggested collection includes wrappers, inference coordination, rollout storage, and updates. The next CPU investigation should include rollout-buffer construction, minibatch indexing, conversion to tensors, and CPU-to-GPU staging. Optimizing the game alone will stop helping once trainer-side overhead becomes dominant.

8. **Hardware and sweep discipline.** EnvPool and PufferLib results vary by core count, NUMA, laptop versus desktop, env variance, and batch size. Before a rewrite, start with 1/8/16 env sweeps, then test 24/32/48 envs only on machines with enough available CPU cores and memory to justify those counts. Sweep workers versus envs-per-worker, Torch thread counts, and pinned-memory transfer if CUDA is active. The winner should be selected by stable end-to-end steps/sec and learning parity, not one short diagnostic.

## Bounded Proofs To Run Before a Rewrite

1. **Latest production-like profile.** Re-run 1/8/16-env profiles after the observation reuse change, then include 24/32/48 envs only where the hardware has enough available CPU cores and memory. Break collection into game step, observation packing, wrapper/frame stack, pipe/shared transport, policy forward, rollout storage, and update time. This tells whether the next bottleneck is still the game.

2. **Env-per-worker prototype.** Keep the current Python game unchanged but make each worker step 2-4 env instances serially and return a batch. Sweep against today's one-env-per-process runner to see whether it helps this workload. Required checks: fixed seed replay equality where expected, no reset/RNG drift, same observation ordering, same episode accounting.

3. **Shared-buffer prototype.** Put observation/reward/done/action arrays in CPU shared memory and send only small control messages/infos. Success means lower collection time at the same policy/training settings, with no change to game semantics.

4. **Selective native micro-POC.** After the latest profile, port only one confirmed hotspot to native code. Good candidates are deterministic packing loops, not physics. Success means replay parity plus measurable end-to-end improvement, not just a faster microbenchmark.

5. **Async/double-buffer prototype.** Test `num_envs > batch_size` or two batches per worker so one batch steps while actions are computed for another. If policy weights remain frozen for the rollout batch, this is mainly an inference-overlap change; if learning updates overlap ongoing collection, it becomes a policy-lag question. Compare both throughput and learning curves.

## Limitations And Behavior Guards

Published multipliers should not be copied onto this game. EnvPool reports large gains for standard environments after C++ integration; PufferLib reports extreme speeds for first-party C environments and more modest but still meaningful vectorization wins for third-party environments; Sample Factory changes the sampling/training architecture. This game already uses native C physics through Pymunk, so "C rewrite" would mainly target Python orchestration around the physics, not the physics solver itself.

Every CPU optimization here needs behavior guards: deterministic replay traces, reset/seed checks, observation equality, reward equality, episode-info equality, and action-order checks. Shared memory and batching are especially easy to get subtly wrong because they can change ordering, reuse stale buffers, or advance RNG streams differently. If an optimization changes the MDP or PPO data distribution, it may increase FPS while hurting time-to-score.

## Practical Takeaway

The best next CPU-side direction is not immediately "rewrite the whole game in C." It is a measured batched-runner prototype: fewer processes, multiple envs per worker, preallocated/shared buffers, and possibly double buffering. If that proves the remaining bottleneck is Python game logic, then selectively compile or rewrite the hottest game loops. A full C environment becomes more attractive only after those smaller proofs show the boundary shape is right and the Python logic itself is the durable bottleneck.
